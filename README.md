## 1. Постановка

В рекомендательной ленте Яндекс Музыки («Моя волна» и персональные плейлисты) трек ставит сервис, человек дослушивает его или пропускает. Это прямой аналог «показ → клик» из условия.

**Задача А (основная, Yambda).**
- **Строка** — алгоритмический показ (`is_organic = 0`) пользователя в день d.
- **Метка** — Listen+: прослушано ≥ 50% трека, как в статье Yambda.
- **Задача модели** — ранжировать показы пользователя внутри дня.
- **Кандидаты** одинаковы для всех методов: залогированные показы. Поэтому сравнивается представление (признаки, модели), а не генерация кандидатов.

**Перенос (KION, X5).**
- Строка — пара (пользователь, кандидат) на целевую неделю.
- Метка — просмотр (KION) или покупка (X5) кандидата за неделю.
- Кандидаты строятся одинаково для всех методов, по истории до начала недели:
  - KION — популярное за 7 дней и iALS, без уже просмотренного;
  - X5 — частые прошлые покупки, популярное и iALS.

**Почему не next-item по всему каталогу.** Тогда результат определял бы генератор кандидатов, а не признаки. Числа в таблицах статьи Yambda получены для другой задачи и с нашими не сравниваются.

## 3. Разбиение и защита от утечек

| | Yambda (дни) | KION / X5 (целевые недели) |
|---|---|---|
| Обучающие строки, этап val | 273–286 | c1, c2, c3 |
| val (A — подбор, B — проверка) | 287–293 | c4 |
| OOT (один прогон) | 294–300 | c5 = последние 7 дней |
| Обучение перед OOT (сдвиг на 7 дней) | 280–293 | c2, c3, c4 |

**Снимок на начало дня — выбранная граница основного сравнения, а не требование задания.** Условие разрешает любую информацию, известную до предсказания. Признаки строки дня d считаются только по событиям с `t < начало дня d`. События самого дня в признаки не попадают: ни метка строки, ни другие показы, ни их порядок. Исключения сделаны только в отдельно помеченных ветках:
- время запроса (раздел 6.5);
- сегодняшняя сессия (раздел 6.7).

**Подбор и проверка:**
- val делится пополам по пользователям, фиксированным хэшем;
- на половине A — отбор признаков, Optuna, ранняя остановка, гипотезы агента;
- половина B — только для отчёта.

**Модели первого уровня, чьи скоры идут в бустинг.**
- Yambda: iALS и Perseus (R4) обучаются на событиях до первого обучающего дня бустинга, отдельно для каждого этапа: для val iALS — до дня 273, Perseus — на метках дней 259–272; для OOT — до дня 280 и на метках 266–279. Вектор пользователя в iALS пересчитывается по истории до начала дня строки, факторы треков фиксированы.
- KION и X5: генератор кандидатов (популярное, iALS) переобучается перед каждой целевой неделей c только на событиях до c. Метка строки лежит в [c, c+7), поэтому модель своей метки не видит. Правило «скользящее», то же, что для признаков.

**Кто попадает в строки KION и X5.** Пользователи, у которых есть история и хотя бы одно действие в целевой неделе. Это стандартный протокол KION: ранжируем для тех, кто пришёл. Отбор одинаков для всех методов, в признаки сам факт прихода не входит.

**Проверки:**
- **инвариантность к обрезке** (`tests/test_no_leakage.py`, `tests/test_generic.py`): признаки на полном логе совпадают с признаками на логе, обрезанном по отсечке, и не меняются при перемешивании всех событий с дня строки. Покрыты B0, B0 на обрезанной истории, вся грамматика обеих сеток (1 127 + 1 295 признаков), признаки агента, аудио, контекст запроса, состояние слушателя и сессионные признаки;
- **признак не зависит от собственной метки строки**;
- **плацебо:** весь поиск R1 на метках, перемешанных внутри пользователь-дня, даёт GAUC 0,500–0,507 при любом K;
- **ворота OOT** (`src/tbrec/freeze.py`):
  - `freeze.json` хранит коммит, ветки, гипотезы, пороги и sha256 всего, от чего зависит скор: строк, выбранной цели, `params.json` каждой ветки и каждого файла признаков;
  - перед каждым скорингом OOT — бустинг, простое правило или Perseus (`scripts/score_r3_oot.py`) — проверяется, что ветка в списке, код не изменён, хэши совпадают и предсказания OOT ещё нет;
  - флага для повторного прогона нет;
- **слепое ревью кода** (LLM, только чтение, `docs/reproducibility_RU.md`) перед заморозкой нашло слабые ворота OOT, ничьи в NDCG, сужение семейства Холма, неточное «равное число признаков» и недетерминированность кандидатов X5. Всё исправлено, добавлены тесты `tests/test_protocol.py`. Остальные находки и почему это не утечки — раздел 11.

## 4. Метрики и правило решений

- **Основные метрики:**
  - GAUC — AUC внутри пользователь-дня (или пользователь-недели), взвешенный по числу строк;
  - NDCG@10 внутри той же группы;
  - группы, где все метки одинаковые, выпадают.
- **Вторичные:** общий ROC-AUC и LogLoss. Общий ROC-AUC в основном различает пользователей между собой, ранжирование внутри группы он почти не видит.
- **Статистика:** парный бутстрэп по пользователям, 1000 повторов; пользователь берётся со всеми своими днями. Для каждого дня отдельно считается, выиграла ли ветка.
- **Правила вердикта** (`src/tbrec/metrics.py`, зафиксированы до OOT):
  - «лучше» — нижняя граница 95% ДИ разности > 0;
  - «хуже» — верхняя граница < 0;
  - «сопоставимо» — ДИ содержит 0 и |Δ| < 0,002 GAUC или 0,003 NDCG@10;
  - иначе — «не определено».
  - Порог 0,002 — практическая граница, выбранная до OOT: на val-B две версии R1, отличающиеся одним признаком (56 и 57), расходятся на 0,0016–0,0017 (`artifacts/runs/r1_*_k56`, `artifacts/runs/r1_*_k57_offbyone`). Разница меньше 0,002 сравнима с эффектом одного признака. Разброс повторной настройки одной и той же конфигурации отдельно не измерялся.
- **Несколько гипотез:** поправка Холма (`scripts/hypotheses.py`).
- **Равный бюджет подбора:**
  - 12 испытаний Optuna на 30% пользователей обучающего окна;
  - ранняя остановка по GAUC на val-A;
  - цель LightGBM выбирается один раз на B0 по val-A и фиксируется: Yambda и X5 — binary, KION — lambdarank.
  - LogLoss для ранней остановки не подошёл: он реагирует на сдвиг общей доли Listen+ между неделями и останавливал обучение слишком рано.

## 5. Бейзлайн B0: LightGBM на ручных признаках

Окна 1, 7, 30 дней и вся история (`src/tbrec/specs.py`, `kion.py`, `x5.py`). В ручной набор включены:
- **пользователь:** активность, доли Listen+, пропусков и органики, лайки, разнообразие, давность;
- **объект:** популярность, доля дослушиваний, лайки и дизлайки;
- **прямые связи пары** (Yambda, X5): сколько раз слушал или покупал, доля дослушиваний, давность;
- **косвенные связи:** пользователь × артист, альбом, жанр, актёр, режиссёр, категория, бренд;
- **демография × объект** (KION, X5).

Базовый блок, общий для всех веток: длина трека, возраст объекта в логе, стаж пользователя, ритм прослушивания; для KION и X5 — ранги генераторов кандидатов и статические атрибуты.

## 6. Исследовательские ветки

### 6.1. R1 — автоматический поиск по грамматике агрегатов

Признак — имя `КЛЮЧ__ФИЛЬТР__АГРЕГАТ__ВЕС`, например `UA__lp__rate__h7d`: «доля прослушиваний этого артиста пользователем, дошедших до Listen+, с периодом полураспада 7 дней».
- **ключи** — сущности и их пары: пользователь, объект, атрибуты объекта, пользователь × атрибут, атрибут пользователя × объект;
- **фильтры** — тип события и порог глубины;
- **агрегаты:** счётчик, сглаженная доля, средняя глубина, давность последнего, возраст первого, число уникальных;
- **вес:** вся история, жёсткое окно `w<n>` или экспоненциальное затухание `h<n>` с периодом полураспада от 6 часов до 365 дней.

Человек задаёт схему данных (какие сущности, атрибуты и типы событий есть) и общий словарь агрегатов и сроков; какие комбинации и сроки взять, решает поиск. Общий движок агрегатов переиспользован через схему (`src/tbrec/generic.py`). Для KION и X5 отдельно заданы схема, фильтры и базовый блок, а также реализована подготовка событий и кандидатов. Атрибуты с несколькими значениями (жанры, актёры) раскладываются по значениям и усредняются. Тест проверяет, что движок по схеме в точности воспроизводит движок Yambda.

**Поиск:**
1. Все кандидаты (Yambda — 1 127 в сетке затухания и 1 295 в сетке окон) считаются на подвыборке отбора.
2. Важности берутся из модели lambdarank (группа — пользователь-день). При бинарной цели gain уходит в признаки пользователя, а их GAUC внутри группы не видит.
3. Кривая top-K на val-A; берётся наименьший K в пределах 0,0005 от лучшего.

Затухающие счётчики потоковые: O(1) на событие, два состояния складываются умножением и сложением.

### 6.2. R2 — скоры моделей и содержание как признаки
- **iALS:** факторы объектов до отсечки, вектор пользователя пересчитывается ежедневно.
- **Аудио:** профиль вкуса — сумма эмбеддингов дослушанных треков с затуханием 30 дней, отдельно профиль пропущенных; признак — косинус трека к профилю.

### 6.3. R3/R4 — Perseus (фреймворк Т-Банка)
- Голова ранжирования по кандидатам; история — прослушивания с долей и органикой, лайки, дизлайки, артист, альбом; история строго до начала дня.
- Конфигурация выбрана на val-A среди трёх вариантов. Победил облегчённый: 256 событий, размер 128, 2 слоя. Конфиг авторов (512 событий, размер 256, 4 слоя) тоже проверен и чуть хуже.
- Бюджет обучения сокращён: при подборе — максимум 3 эпохи, ранняя остановка по val-A с patience=1. В исходных конфигах авторов — 30 эпох и patience=5 (`docs/reproducibility_RU.md`, `external/perseus_adapter/stage2.py`). Поэтому проверена адаптация Perseus с ограниченным обучением, а не полный опубликованный режим. Влияние этого ограничения отдельно не измерено.
- R4 — скор Perseus как признак бустинга. Perseus для этого обучен до первого обучающего дня бустинга: на метках дней 259–272 для val и 266–279 для OOT.
- Раздельные лимиты истории по типам событий (H6) эффекта не дали: 0,5519 против 0,5520.

### 6.4. R5 — LLM-агент, генерирующий гипотезы
- LLM (только чтение, без доступа к данным) видит грамматику, текущий набор с важностями и журнал прошлых раундов и предлагает 10 признаков. Это имена грамматики или составные `ratio(a,b)` и `diff(a,b)`.
- Каждое предложение проходит тест инвариантности и детерминированную оценку прироста на val-A (порог +0,001).
- 3 раунда, журнал — `artifacts/r5_state.json`.

### 6.5. Время запроса (контекст)
- Час, часть суток и день недели самого показа плюс история пользователя, трека и артиста в это время. Например, «доля Listen+ этого человека в эту четверть суток».
- Это меняет постановку с «набора на начало дня» на «ранжирование в момент запроса», поэтому ветки сравниваются парой: ручной контекст против найденного поиском.

### 6.6. Состояние слушателя
- Эмоций в логе нет, их заменяет звучание × время: близость трека к тому, что человек дослушивает в эту часть суток; вчерашний профиль против привычного; 32 кластера звучания как «настроения без названий» в грамматике.
- Кластеризация использует только содержание треков, без меток.

### 6.7. Потоковое расширение (сессия)
- Опорная точка, не участник основного сравнения.
- Признаки — исходы сегодняшних прослушиваний пользователя строго раньше показа: события из того же 5-секундного интервала исключены, промежутки по времени не используются (если метка — конец прослушивания, промежуток выдал бы длину текущего).

### 7.5. После заморозки: метка-лестница (вне гипотез, только val-B)

Вопрос: сохраняется ли выигрыш автопоиска, если учить модель различать не только «дослушал или нет», но и глубину прослушивания.

- **Как обучали:** B0 и R1 переобучены с lambdarank на этой метке. Признаки те же, гиперпараметры — замороженные, без нового подбора. Ранняя остановка — по NDCG@10 лестницы на val-A, отчёт — на val-B. OOT не трогали.

## 8. Анализ: что сработало, что нет и почему

**1. Поиск агрегатов дал выигрыш в Yambda.** R1 лучше B0 на OOT и при равном числе отбираемых агрегатов. В KION преимущество сохранилось только по NDCG@10, в X5 результаты сопоставимы. Это сравнение с конкретным ручным набором B0, а не с работой инженера вообще (`artifacts/compare_oot_eval.json`, те же файлы в `artifacts/kion/` и `artifacts/x5/`).

В отобранных наборах различаются связи: в музыке часто встречается пользователь × трек, в кино — атрибуты тайтла и демография, в продуктах — повторные покупки и категории. По-видимому, в этих доменах важны разные связи. Для нового домена всё равно нужны подготовка данных и описание схемы (`artifacts/r1_decay_selected.json`, те же файлы в `artifacts/kion/` и `artifacts/x5/`).

**2. Поиск по затуханию не оказался лучше поиска по окнам.** При равном числе признаков он хуже в Yambda и X5, в KION результаты сопоставимы. Для каждой сетки поиск отбирал свой набор. Отдельно влияние формы веса здесь не проверялось. Чтобы проверить именно её, нужно оставить одинаковыми ключи, фильтры и агрегаты, меняя только вес; такого опыта не было (`artifacts/hypotheses_oot_eval.json`, соответствующие файлы двух других доменов).

**3. Время запроса дало дополнительный сигнал.** Ручной контекст лучше найденного поиском; разница между ними −0,0069 GAUC. В отборе поиск предпочёл более короткие периоды. Возможно, поиск подогнал набор под неделю val-A. Отдельно эта причина не проверялась. Эта ветка получает время запроса и потому выделена из основного сравнения снимков (`artifacts/hypotheses_oot_eval.json`, `artifacts/r1_ctx_selected.json`).

**4. В R5 прошла отбор одна гипотеза из тридцати.** Она описывает изменение личного дослушивания артиста на коротком и длинном горизонтах. Здесь проверялось, что агент добавит к готовой грамматике. Другие семейства признаков, например текстовые, в этот опыт не входили (`artifacts/r5_state.json`, `artifacts/r5_accepted.json`, `artifacts/compare_oot_eval.json`).

**5. Perseus полезнее оказался в составе бустинга.** Отдельная модель хуже B0, добавление её скора улучшает B0. Ограничение истории — одно из возможных объяснений: при обрезке пользовательской истории B0 до последних 256 событий GAUC снижается на 0,0207. Глобальные агрегаты объектов в этом опыте сохраняют полную историю, а архитектура и обучение отличаются от Perseus. По этой абляции нельзя определить, какая часть отставания трансформера объясняется длиной истории (`artifacts/compare_oot_eval.json`).

Более крупная конфигурация и раздельные лимиты истории не улучшили результат облегчённой модели. Другие варианты настройки Perseus не проверялись. Чтобы разделить влияние истории, обучения и адаптера, нужны отдельные опыты на val, без повторного обращения к исходному OOT (`artifacts/final_val_B.json`, `artifacts/runs/r3_perseus/`).

**6. Аудио помогает на новых артистах.** В этом срезе прирост аудио выше, чем у R1. По-видимому, содержание трека частично компенсирует отсутствие истории пары. Причину разницы по одному срезу определить нельзя (`artifacts/slices_oot_eval.md`).

**7. Часть идей не улучшила результат.** Отбор по устойчивости во времени проиграл B0. Возможная причина — шум оценок на отдельных днях; устойчивость сама по себе здесь не была полезным критерием. Признаки состояния слушателя поверх времени запроса заметного дополнительного выигрыша не дали, хотя модель использует их. По-видимому, часть их информации уже содержится в других признаках (`artifacts/compare_oot_eval.json`, `artifacts/r1_decay_stable3_selected.json`, `artifacts/shap_oot.json`).

**8. Повторы и сессия требуют разных проверок.** У двух соседних показов одного трека в пределах дня исход совпадает в 69% случаев при 51% для случайного совпадения. Это описательная проверка на днях до OOT, не численная оценка потолка качества (`artifacts/label_checks.json`).

Без строк, где трек уже звучал раньше в тот же день, прирост сессионной ветки составляет +0,0902 [+0,0820; +0,0984] GAUC на val-B. Прирост сохраняется после удаления этих строк. Проверка относится к повторным целевым строкам; она не устанавливает происхождение всех событий и доступность исходов в реальном сервисе. Неопределённость смысла timestamp остаётся ограничением (раздел 11; `artifacts/label_checks.json`).

**9. Listen+ недостаточно для оценки ленты.** При ранжировании по Listen+ растёт доля повторов и снижается доля новых артистов в первых позициях. Поэтому прирост основной метрики я бы проверял вместе с новизной и разнообразием. Пример такого ограничения приведён в разделе 10; его порог предложен после OOT и не является частью замороженных гипотез (`artifacts/guardrails_oot_eval.md`).

**10. Важность признаков не равна их отдельному вкладу.** У бинарной модели высоко стоят признаки пользователя, постоянные внутри пользователь-дня. Сами по себе они не задают порядок треков, но могут влиять через взаимодействия. SHAP и важности ранжирующей модели помогают разобрать результат. Отдельный вклад признаков нужно проверять абляциями (`artifacts/shap_oot.json`, `artifacts/r1_decay_selected.json`).

## 10. Что проверять дальше и по какому критерию

Следующий эксперимент я бы провёл с R1, iALS, аудио, скором Perseus и ручным контекстом времени запроса в составе бустинга. Их польза показана в отдельных сравнениях, но итоговая сборка с контекстом на OOT не оценивалась. Сначала её нужно сравнить на val, затем проверять в A/B. Исходный OOT для этого повторно не используется.

**Критерий A/B.** Основная метрика — доля Listen+ на пользователя в рекомендательной ленте. Дополнительно я бы контролировал долю новых артистов в первых 10 позициях. Пример ограничения — снижение относительно B0 не больше 1 п.п. Это предложение после OOT, а не заранее проверенный продуктовый порог.

На готовом OOT доля новых артистов у B0 — 15,0%, у R1 — 13,7%, у полного стека — 14,6%, у ручного контекста — 15,2%. По предложенному ограничению R1 отдельно не прошёл бы, полный стек и контекст — прошли бы (`artifacts/guardrails_oot_eval.md`). Если качество растёт ценой нарушения ограничения, нужно пересмотреть цель или ранжирование и снова проверить на val.

В реализации можно начать с ежедневных признаков и офлайн-скора Perseus. Счётчики с затуханием допускают потоковое обновление, но задержка и стоимость такого сервиса здесь не измерялись. Сессионные признаки потребуют отдельной проверки времени доступности событий. Цель обучения тоже стоит выбирать под продуктовую метрику: лестница лучше различает глубину, бинарная метка — Listen+; отдельная цель для лайка остаётся гипотезой (`artifacts/graded_label.json`).

## 11. Ограничения

- **Снимок на начало дня ограничивает доступную информацию.** Текущая сессия в основное сравнение не входит; её признаки исследованы отдельно на val.
- **Метка Listen+ поощряет «безопасные» повторы.**
- **Масштаб проверки ограничен.** Yambda-500M и 5B не проверялись. По имеющимся результатам нельзя отделить влияние размера выборки от архитектуры и настройки.
- **Время в Yambda относительное.** Неизвестно, означает timestamp начало, конец прослушивания или запись в лог. Проверки подтверждают отсечение по принятой оси времени, но не фактическую доступность played_ratio в сервисе. Это допущение основного снимка и особенно сессионной ветки.
- **В KION и X5 val и OOT — по одной неделе,** ДИ широкие.
- **Ничьи в ранней остановке.** Функция ранней остановки (`gauc_feval`) на этапе val разбирала ничьи последовательно, а не средним рангом. Ничьи — это в основном повторы одного трека в пользователь-дне с одинаковыми признаками. Разные наборы признаков дают разные ничьи, поэтому влияние на подбор у веток может различаться; мы его не измеряли. Итоговые GAUC всегда считались со средними рангами, NDCG — с порядком ничьих, не зависящим от порядка строк. Чтобы не менять протокол посреди эксперимента, функция оставлена как была.
- **Кандидаты X5.** Строки построены до исправления недетерминированности: ничьи на границе топ-40 частых товаров клиента. Таблица строк зафиксирована хэшем в заморозке. Повторная сборка на текущем коде воспроизводит протокол, но может разойтись с ней на ничьих.
- **Потоковые ветки** (сессия) нарушают снимок на начало дня по построению. Это опорная точка, только на val, в прогон OOT они не входят.

## 14. Как воспроизвести

Сохранённые манифесты заморозки, параметры и OOT-результаты не перезаписываются. Коммит `db1a3920ea3d897566541b9966bf995bec45ce9f` является опубликованным эквивалентом состояния исходного эксперимента и не использовался в историческом запуске. Текущая версия содержит последующие проверки, пояснения и средства воспроизведения; она не объявляется новой заморозкой. Новые коммиты сохраняют исходный коммит в истории, но текущий HEAD отличается от него, поэтому ворота исторического OOT намеренно не разрешают повторный скоринг.

Копирование неизменённых байтов сохраняет SHA256 файлов. Удаление Git-истории убирает возможность проверить исходный коммит по истории поставки; переписывание истории меняет идентификаторы коммитов. В этой работе исходные коммиты и манифесты сохранены.

**Переносы строк тоже входят в хэш.** Исторический запуск выполнен в Windows. Например, `artifacts/runs/b0/params.json` в рабочем каталоге имеет CRLF и совпадает с SHA256 в заморозке; Git хранит тот же текст с LF. Поэтому экспорт из Git или checkout с другими настройками переносов может дать другой байтовый хэш при тех же значениях JSON. Манифест описывает файлы исходного запуска, а не любой новый clone; пересчитывать его под экспорт нельзя.

Маршруты обучения предназначены для отдельного рабочего clone. Маршрут B заканчивается на val. Для технического повторения исторического OOT нужен отдельный clone и собственная заморозка; такой повтор не является новым независимым тестом. Текущие ворота отвергнут изменённый код или уже существующее предсказание.

Окружение: Python 3.12, `uv` (`python -m pip install uv`), Git Bash для `.sh`. Команды ниже выполняются в окружении проекта: после `python -m uv sync` активировать его (`source .venv/Scripts/activate`). Очереди сами вызывают `.venv/Scripts/python.exe`.

**A. Без данных.** Таблицы, манифест заморозки (`artifacts/freeze.json`, опубликованный эквивалент исторического коммита `db1a3920ea3d897566541b9966bf995bec45ce9f`), параметры и метрики каждой ветки лежат в `artifacts/`. Рисунок 1 пересобирается из них: `python scripts/figures.py`.

**B. Основной результат с нуля (Yambda, B0 и R1).**

1. Байтовые хэши новых Parquet могут отличаться при том же содержимом из-за метаданных и записи формата. Эта проверка не пересобирает строки задачи, признаки или модели и не выполняет скоринг. Полный цикл обучения на чистой машине здесь не повторялся.


## 15. Использование ИИ

Математика обсуждалась с ИИ в формате брейншторма. Автор предлагал гипотезы, выбирал и интерпретировал метрики, задавал методику проверок и условия их прохождения, выбирал дополнительные датасеты.

Для подготовки кода, запуска расчётов и черновиков использовались ИИ-инструменты Anthropic и OpenAI. LLM также использовалась для рецензирования кода в режиме только чтения и генерации гипотез R5. В R5 модель видела грамматику, текущий набор и журнал val-A, без доступа к данным и меткам. Шаблон, оценка и результаты сохранены в `scripts/r5_prompt.py`, `scripts/r5_eval.py`, `artifacts/r5_state.json` и `artifacts/r5_accepted.json`.
