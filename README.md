# Можно ли не придумывать признаки руками? Автоматический поиск агрегатов и Perseus против бустинга на Yambda

Тестовое задание Т-Банка: сильный градиентный бустинг на ручных признаках против автоматизации построения признаков и обучаемых представлений.

> Статус: в работе. Разделы с результатами заполняются по мере прогонов. Числа OOT появятся один раз, после заморозки пайплайна.

## 1. Постановка

**Продуктовая рамка.** «Моя волна» Яндекс Музыки: лента, где трек играет сам. Сервис показал трек; пользователь дослушал его или пропустил.

**Задача А (основная): ранжирование показов.**
- Объект — алгоритмический показ (`is_organic = 0`) пользователя в течение дня.
- Метка — Listen+: прослушано ≥ 50% трека (как в статье Yambda).
- Модель ранжирует показы пользователя внутри дня. Это прямой аналог «показ → клик» из условия.
- Кандидаты одинаковы для всех методов — залогированные показы. Поэтому сравнивается именно представление (признаки, модели), а не генерация кандидатов.

**Почему не next-item по каталогу.** Тогда качество определял бы в первую очередь генератор кандидатов, а не признаки. Такая постановка — задача Б в плане (кандидаты из повторов, ItemKNN/iALS и Perseus, затем реранк). На неё не хватило срока, см. раздел 9.

## 2. Данные

[Yambda-50M](https://huggingface.co/datasets/yandex/yambda), плоский формат:
- 9 238 пользователей с полной историей — условие задания о сэмплировании выполнено по построению;
- 877 тыс. треков, 46,5 млн прослушиваний, 0,88 млн лайков, 0,11 млн дизлайков;
- время — секунды от начала лога, округлены до 5 с, всего 301 день;
- у прослушивания есть `played_ratio_pct`, `is_organic` и длина трека; есть маппинги трек → артист и трек → альбом, аудио-эмбеддинги.

Дни отсчитываются от конца лога: день 300 — ровно последние 24 часа, тестовый день Global Temporal Split из статьи.

| | Значение |
|---|---|
| Алгоритмических показов в день | ≈ 85–117 тыс. |
| Активных пользователей в день | ≈ 2,7–3,3 тыс. |
| Доля Listen+ среди алгоритмических показов | 0,66–0,72 |
| Доля показов уже слушанного пользователем трека | 55% |

## 3. Разбиение и защита от утечек

Тестового набора в задании нет, поэтому OOT собран из конца лога.

| Часть | Дни | Зачем |
|---|---|---|
| Обучающие строки | 273–286 (14 дней) | обучение бустинга (этап val) |
| val | 287–293 (7 дней) | весь подбор: признаки, гиперпараметры, гипотезы агента |
| OOT | 294–300 (7 дней) | один финальный прогон |
| Обучающие строки для OOT | 280–293 | переобучение со сдвигом на 7 дней, параметры и число деревьев заморожены |

- **Снимок на начало дня.** Признаки строки дня d считаются только по событиям с `t < начало дня d`. События самого дня в признаки не попадают, включая метку строки, другие показы этого дня и время показа внутри дня. Показы ранжируются как набор на начало дня.
- **val делится по пользователям пополам** (фиксированный хэш):
  - A — отбор признаков, Optuna, ранняя остановка;
  - B — чистые числа val.
- **Модели первого уровня** (iALS, Perseus), чьи скоры идут в бустинг, обучаются только на событиях до первого обучающего дня бустинга: до 273 для val, до 280 для OOT. Иначе их скоры на обучающих строках посчитаны на тех же метках.
- **Тесты** (`tests/test_no_leakage.py`):
  - признаки, посчитанные на полном логе, совпадают с посчитанными на логе, обрезанном по отсечке;
  - признаки не меняются, если перемешать все события начиная с дня строки;
  - признаки не зависят от собственной метки строки.

  Проверяются B0, вся грамматика R1 (2 254 признака) и все признаки, предложенные агентом.
- **OOT — один раз.** `scripts/run_branch.py --stage oot` не запускается без `artifacts/freeze.json` и не перезаписывает готовый прогон.

## 4. Метрики и правило сравнения

- **Основные:** GAUC (AUC внутри пользователь-дня, взвешенный по числу показов) и NDCG@10 внутри пользователь-дня.
- **Вторичные:** ROC-AUC и LogLoss.
- Пользователь-дни, где все метки одинаковые, из основных метрик выпадают.
- Основные метрики не видят признаков пользователя: внутри группы они константны и работают только через взаимодействия в деревьях.
- **Статистика:** парный бутстрэп по пользователям, 1000 повторов; пользователь берётся со всеми своими днями. Дополнительно — метрика по каждому дню OOT и число дней из 7, где Δ > 0.
- **Решающие слова** (зафиксированы до OOT, `src/tbrec/metrics.py`):
  - «лучше» — нижняя граница 95% CI для Δ > 0;
  - «хуже» — верхняя граница < 0;
  - «сопоставимо» — CI содержит 0 и |Δ| < 0,002 GAUC или 0,003 NDCG@10;
  - иначе — «не определено».
- **Равный бюджет подбора:** у финальной модели каждой ветки 12 испытаний Optuna на одних и тех же данных.

## 5. Бейзлайн B0: LightGBM на ручных признаках

Окна 1, 7, 30 дней и вся история; 56 агрегатов плюс базовый блок.
- **Пользователь:** активность, доли Listen+, пропусков и органики, лайки, число уникальных треков, давность.
- **Трек:** популярность, доли Listen+ и пропусков, доля рекомендательных прослушиваний, лайки и дизлайки.
- **Артист и альбом:** популярность, доля Listen+.
- **Пара, прямые связи:** сколько раз слушал, сколько раз дослушал, средний played_ratio, давность, лайк, дизлайк.
- **Пара, косвенные связи:** пользователь × артист и пользователь × альбом — счётчики, доли, давность, лайки.
- **Базовый блок (общий для всех веток):** длина трека, возраст трека в логе, стаж пользователя, ритм прослушивания (активные дни, регулярность, время суток).
- Доли сглажены к глобальному уровню до отсечки.

Список признаков — `src/tbrec/specs.py`.

## 6. Исследовательские ветки

- **R1 — автоматический поиск в грамматике агрегатов.**
  - Признак — имя `КЛЮЧ__ФИЛЬТР__АГРЕГАТ__ВЕС`, аналог `SELECT agg(...) WHERE filter GROUP BY key`:
    - ключи U, I, A, L, UI, UA, UL;
    - фильтры listen, Listen+, skip, organic, algo, like, dislike;
    - агрегаты: счётчик, сглаженная доля, средний played_ratio, давность, возраст, число уникальных.
  - Вместо окна «7 дней» — экспоненциальное затухание с периодом полураспада τ ∈ {6 ч, 1, 3, 7, 14, 30, 90, 365 дней, ∞}. Это ответ на вопрос «почему 7, а не 10». Затухающие счётчики потоковые: O(1) на событие, слияние двух состояний — умножение и сложение.
  - Поиск: все 1 127 кандидатов считаются на подвыборке → важность → отбор по GAUC на val-A → проверка на val-B.
  - Тот же поиск по сетке жёстких окон проверяет H4.
- **R2 — скоры моделей как признаки:** iALS, аудио-косинус трека к профилю пользователя.
- **R3 — Perseus** (фреймворк Т-Банка) сам по себе: голова ранжирования по кандидатам; история — прослушивания с played_ratio, лайки и дизлайки, органика, артист и альбом.
- **R4 — гибрид:** B0 + скор Perseus. Так советуют использовать Perseus при сильных ручных признаках сами авторы.
- **R5 — цикл гипотез агента:** Codex видит таблицу результатов и реестр признаков и предлагает новые имена в грамматике. Каждое проходит тесты утечек и оценку на val-A; ведётся журнал попыток.

**Гипотезы:**
- H1: R1 не хуже B0;
- H2: R3 хуже B0 — ожидание авторов Perseus;
- H3: B0 + Perseus лучше B0;
- H4: затухание с подобранным τ не хуже жёстких окон при равном числе признаков;
- H6: раздельные лимиты истории по типам событий лучше обрезки по давности.

## 11. Как воспроизвести

```bash
python -m uv sync                          # Python 3.12, torch cu126
python scripts/download_yambda.py          # ~0.4 GB (+ --embeddings, 13.8 GB)
python -c "import sys; sys.path.insert(0,'src'); from tbrec.data import prepare; prepare()"
python scripts/build_features.py rows
python scripts/build_features.py b0
python -m pytest -p no:cacheprovider tests  # leakage tests
python scripts/run_branch.py b0 --stage val
python scripts/compare.py --stage val --part val_B --base b0 b0 r1_decay ...
```

Процессы ограничены 5 потоками и пятью последними логическими ядрами, чтобы машина оставалась отзывчивой (`src/tbrec/__init__.py`).
